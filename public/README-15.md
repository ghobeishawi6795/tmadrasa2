# قدم ۱۵ — فاز ۵ راهنما: زیرساخت و مقیاس‌پذیری

## چه چیزی ساخته شد

### ۱) Backup — چون Cloudflare D1 خودکار export نداره و R2 هم نداریم

راه‌حل واقعی برای این پروژه (بدون هیچ blob storage) یک **خروجی دستی/قابل‌اسکریپت**
بود، نه یک Cron خودکار:

- `GET /api/admin/backup` — تمام داده‌های همین مدرسه (دانش‌آموزان، کلاس‌ها،
  نمرات، حضور و غیاب، تکالیف، پیام‌ها، آزمون‌ها و ...) رو به‌صورت یک JSON
  واحد برمی‌گردونه. `password_hash` عمداً از خروجی حذف شده — یک فایل پشتیبان
  نباید رمز عبور کسی رو نگه داره.
- توی پنل مدیر، بخش «تنظیمات» (که قبلاً غیرفعال بود) الان یک دکمه‌ی
  «دانلود خروجی پشتیبان» داره که همین API رو صدا می‌زنه و فایل JSON رو
  مستقیم دانلود می‌کنه.

**این خودکار نیست** — باید یا خودتون این دکمه رو مرتب (مثلاً هفته‌ای یک‌بار)
بزنید، یا اگه می‌خواید کاملاً خودکار بشه، یک اسکریپت خارجی (مثلاً یک
GitHub Action رایگان با یک cron schedule) بنویسیم که این endpoint رو صدا
بزنه و نتیجه رو جایی مثل Google Drive یا یک ایمیل ذخیره کنه. اگه بخواید،
قدم بعدی همینه.

### ۲) Health-check — چون Cloudflare خودش هشدار قطعی نمی‌ده

`GET /api/health` (بدون نیاز به ورود) — یک پینگ ساده که وضعیت اتصال به D1
رو برمی‌گردونه. **این خودش چیزی رو مانیتور نمی‌کنه** — باید یک سرویس رایگان
بیرونی (پیشنهاد: [UptimeRobot](https://uptimerobot.com) یا
[Better Uptime](https://betteruptime.com)، هر دو پلن رایگان دارن) هر
چند دقیقه این آدرس رو چک کنه و اگه جواب نداد بهتون پیامک/ایمیل بده. این
دقیقاً همون «Monitoring ساده» بود که فاز ۵ خواسته بود.

### ۳) محدودیت حجم سمت سرور — تکمیل همون کاری که تو قدم ۱۳ شروع شده بود

قدم ۱۳ فقط `answer_data` (عکس/صدای تکلیف) رو به ۵۰۰KB محدود کرده بود. حالا
یک helper مشترک (`requireMaxLength`) اضافه شد و روی همه‌ی فیلدهای متنیِ
بدون‌محدودیتِ قبلی اعمال شد:
- متن پیام: حداکثر ۵۰۰۰ نویسه
- عنوان/متن اطلاعیه: ۲۰۰ / ۱۰,۰۰۰ نویسه
- متن پاسخ تکلیف (نوع «متنی»): ۲۰,۰۰۰ نویسه

این‌ها همیشه **سمت سرور** چک می‌شن، نه فقط `maxlength` روی input فرانت‌اند —
دقیقاً همون نکته‌ای که راهنما تأکید کرده بود.

## درباره‌ی برآورد ترافیک (فاز ۵، بخش اول)

این یکی کد نیست، یک تخمینه که باید خودتون باهاش تصمیم بگیرید:

Cloudflare Pages Functions پلن رایگان: **۱۰۰,۰۰۰ درخواست در روز**. برای یک
مدرسه‌ی متوسط (مثلاً ۳۰۰ دانش‌آموز + ۲۰ معلم + والدین)، اگه هر کاربر روزی
~۲۰-۳۰ درخواست API بزنه (باز کردن چند صفحه، چک کردن نمره، ارسال تکلیف)،
یعنی روزی حدود ۱۰,۰۰۰-۱۵,۰۰۰ درخواست برای **یک** مدرسه. یعنی پلن رایگان
برای **۲-۳ مدرسه‌ی هم‌زمان** جواب می‌ده، ولی برای عرضه‌ی عمومی به چندین
مدرسه، باید Plan پولی Cloudflare Workers (۵ دلار/ماه، ۱۰ میلیون درخواست)
رو فعال کنید. D1 پلن رایگان هم ۵ میلیون خواندن/روز و ۱۰۰هزار نوشتن/روز
داره — برای همون مقیاس، معمولاً نوشتن (ثبت نمره/حضور/پیام) زودتر از خواندن
به سقف می‌رسه.

**جمع‌بندی:** برای تست با ۱-۲ مدرسه‌ی واقعی، پلن رایگان کافیه. قبل از عرضه‌ی
عمومی به چند مدرسه هم‌زمان، پلن Workers Paid رو فعال کنید.

## چیزی که هنوز باقی مونده (از فاز ۵)

- **خودکارسازی واقعی backup** (نه فقط دکمه‌ی دستی) — نیاز به یک اسکریپت
  خارجی جدول‌زمانی (مثلاً GitHub Actions) داره؛ اگه بخواید می‌سازمش.
  - همچنین برای این هم پیشنهاد میدم دوباره بحث R2 پیش بیاد — چون بدون
    یک storage واقعی، بک‌آپ‌ها فقط به‌صورت دستی داخل مرورگر دانلود می‌شن
    و جایی روی سرور نگه‌داری نمی‌شن.

## تست کردن

```bash
wrangler pages dev public --d1=DB --local
```

با `admin_a` وارد شو، برو «تنظیمات» → «دانلود خروجی پشتیبان». همچنین
`curl http://127.0.0.1:8788/api/health` رو مستقیم تست کن (نیازی به توکن نداره).
