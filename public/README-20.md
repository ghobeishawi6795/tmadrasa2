# قدم ۲۰ — رفع کامل مشکل XSS (escape سراسری ورودی کاربر)

## خلاصه
همون‌طور که تو README-19 به‌عنوان یک TODO امنیتی جدی ثبت شده بود: هیچ‌جای اپ ورودی‌های کاربر قبل از `innerHTML` escape نمی‌شدن. این قدم یک pass کامل و سراسری روی هر ۴ داشبورد (admin/teacher/student/parent) + register.html بود.

## چیزی که اضافه شد
دو تابع مشترک جدید در `public/assets/js/app.js` (که تو `<head>` هر ۴ صفحه، قبل از استفاده، لود می‌شه):

- **`escapeHtml(value)`** — escape استاندارد HTML entity (`& < > " '`) برای هر متنی که قراره به‌عنوان **محتوای متنی** داخل یک template literate که به `innerHTML` می‌ره درج بشه. مقدار غیر-رشته‌ای (null/undefined/عدد) هم امن مدیریت می‌شه.
- **`escapeAttr(value)`** — برای جاهایی که یک مقدار (معمولاً یک آبجکت یا رشته) باید داخل یک **attribute مثل `onclick="..."`** جاسازی بشه، طوری که هم دابل‌کوتیشن attribute و هم مقدار داخلش امن بمونن. جایگزین الگوی قدیمی و شکننده‌ی `onclick='...${JSON.stringify(a)}...'` یا `'${x.replace(/'/g, "")}'` شد.

## جاهایی که اصلاح شد

### ۱) همه‌ی نمایش‌های متن کاربر در `innerHTML`
هر جایی که یک فیلد از سرور (اسم دانش‌آموز/معلم/والد، عنوان تکلیف/آزمون/اطلاعیه، توضیحات، بازخورد نمره، پیام چت، متن سؤال، پاسخ کوتاه دانش‌آموز، نام کلاس/درس، دلیل رد در ایمپورت HTML و...) مستقیم تو یک template literate درج می‌شد، حالا با `escapeHtml(...)` پیچیده شده. این شامل هر ۴ داشبورد + پنجره‌های print (کارنامه‌ی چاپی دانش‌آموز و والد) می‌شه.

**استثناها (عمداً escape نشدن چون از قبل امن بودن):**
- عنوان‌های `openModal(title, ...)` — پارامتر اول با `textContent` ست می‌شه، نه `innerHTML`، پس ذاتاً امنه.
- مقادیر عددی (id، نمره، شمارنده) و enum‌های ثابت سمت سرور (وضعیت‌ها).
- `data:` URI ها (عکس/صدا) — اینا escape نمی‌شن چون کاراکتر خطرناکی ندارن و escape کردنشون می‌شکوندشون.
- برچسب‌های ثابت hardcode شده تو کد (مثل `NAV_ITEMS`).

### ۲) رفع ۹ مورد واقعی «شکستن attribute» (attribute-breakout)
چند جا از الگوی زیر استفاده شده بود:
```js
onclick="openConversation(${c.id}, '${(c.title || "گفتگو").replace(/'/g, "")}')"
```
مشکل: attribute با `"` باز می‌شه، پس اگه `c.title` یک کاراکتر `"` داشته باشه (نه حتی کوتیشن تکی)، attribute زودتر از موعد می‌بندید و هرچی بعدش بیاد به‌عنوان HTML خام تفسیر می‌شه — یعنی یک XSS واقعی، نه فقط یک باگ ظاهری. جاهایی که این الگو بود: `openAssignForm` و `openLinkChildForm` (ادمین)، `openConversation` (هر ۴ داشبورد)، `openSubmissionsList` و `submitAssignmentGrade` (معلم). همه با `escapeAttr(...)` جایگزین شدن.

همچنین یک مورد `onclick='openAssignmentDetail(${JSON.stringify(a)})'` (کوتیشن تکی دور یک آبجکت کامل JSON) در پنل دانش‌آموز که دقیقاً همون ریسک از README-19 بود — با `onclick="openAssignmentDetail(${escapeAttr(a)})"` جایگزین شد.

### ۳) `<textarea>` و attributeهای `value=""`
مقادیر preexisting که داخل `<textarea>...</textarea>` (متن سؤال هنگام ویرایش، متن مرجع تصحیح دستی) یا `value="..."` (نام برندینگ مدرسه، متن گزینه‌ی چندگزینه‌ای، بازخورد نمره‌ی تکلیف) قرار می‌گرفتن هم escape شدن — بدون این کار، یک `</textarea>` یا `"` داخل مقدار می‌تونست از تگ خارج بشه.

## نتیجه
هیچ‌جای اپ دیگه بدون escape، ورودی کاربر رو مستقیم به `innerHTML`/attribute تزریق نمی‌کنه. این مشکل قدیمی که از قدم‌های خیلی قبل‌تر وجود داشت، الان کامل رفع شده — نه فقط جاهای جدید.

## تست
هر ۴ فایل با `node --check` سینتکسشون تأیید شد (بدون خطا). تست دستی روی یک دیپلوی واقعی هنوز لازمه — پیشنهاد می‌شه بعد از دیپلوی این نسخه، یک اسم/عنوان حاوی `<b>test</b>` یا `"><img src=x onerror=alert(1)>` امتحان کنی تا مطمئن بشی به‌صورت متن خام نمایش داده می‌شه، نه اجرا.
