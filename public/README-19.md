# قدم ۱۹ — باگ‌یابی کامل زیپ قبلی + فاز ۳ (تکالیف تعاملی خودکار-تصحیح)

## بخش ۱: باگ‌یابی زیپ step18 — ۳ باگ واقعی پیدا و رفع شد

### باگ ۱ (کوچک): کارنامه‌ی والد همیشه «بدون دوره» نشان می‌داد
`functions/api/parent/grades.js` برخلاف نسخه‌ی دانش‌آموز (`student/report-card.js`)، هیچ‌وقت `grade_period` رو واکشی/برنمی‌گردوند. رفع شد — حالا دقیقاً همون منطق دانش‌آموز رو داره (جدیدترین دوره به‌صورت پیش‌فرض).

### باگ ۲ (⚠️ جدی): نمرات تکلیف و امتحان اصلاً وارد کارنامه نمی‌شدند!
این مهم‌ترین یافته بود. `/api/teacher/submissions` (تصحیح تکلیف) و مسیر پایان امتحان (`student/exam-attempt.js` + `teacher/grading.js`) فقط جدول `submissions`/`exam_attempts` رو آپدیت می‌کردن، ولی **هیچ‌وقت ردیفی تو جدول `grades` نمی‌ساختن**. کارنامه (`buildReportCard`) فقط از جدول `grades` می‌خونه — پس تا امروز، تنها راهی که نمره‌ای تو کارنامه ظاهر می‌شد این بود که معلم دوباره، دستی، از تب «نمرات» همون نمره رو یک‌بار دیگه وارد کنه!

رفع شد با یک helper جدید مشترک: `functions/api/_shared/grades-sync.js` — تابع `syncGradeFromSource()` که الان از هر ۳ مسیر واقعی نمره‌دهی صدا زده می‌شه (تصحیح تکلیف، پایان خودکار امتحان، پایان تصحیح دستی امتحان) و بدون نیاز به ورود دوباره، خودش ردیف `grades` رو می‌سازه/آپدیت می‌کنه.

### باگ ۳ (⚠️ جدی، نتیجه‌ی مستقیم باگ ۲): میانگین کارنامه با نمره‌های غیرهم‌مقیاس اشتباه محاسبه می‌شد
کد `buildReportCard` از قبل یک کامنت هشدار داشت: «این فرمول فرض می‌کنه همه‌ی نمرات یک درس sameمقیاس (مثلاً از ۲۰) هستن؛ اگه یک درس نمرات با max_score متفاوت داشته باشه، قبل از اعتماد به این عدد باید نرمال‌سازی درصدی انجام بشه.» با فعال‌شدن sync خودکار (باگ ۲)، این شرط دقیقاً محقق می‌شد: مثلاً یک تکلیف تطبیقی از ۱۰ نمره کنار یک امتحان از ۱۰۰ نمره تو همون درس. رفع شد — `reportcard.js` حالا هر ردیف رو اول به درصد نرمال می‌کنه (دقیقاً همون روش که `admin/reports.js` از قبل برای میانگین کلاس استفاده می‌کرد)، بعد نتیجه رو به مقیاس آشنای «از ۲۰» برمی‌گردونه تا هیچ تغییری تو UI لازم نباشه.

### یافته‌ی مهم که رفع نشد (نیاز به کار بزرگ‌تر جدا داره)
**هیچ‌جای این پروژه ورودی‌های کاربر escape نمی‌شن** (نه اسم، نه پیام، نه عنوان تکلیف) قبل از `innerHTML`. این یعنی تئوری stored-XSS در سراسر اپ وجود داره (مثلاً اگه یک اسم دانش‌آموز حاوی `<script>` باشه). این یک مشکل قدیمی و سراسریه، نه چیزی که تو این قدم ایجاد شده باشه — رفعش نیاز به یک pass جدا و کامل روی همه‌ی صفحات داره. فعلاً پیشنهاد میشه به‌عنوان یک TODO امنیتی جدی نگهش داری.
همچنین: چند جا از الگوی `onclick='...${JSON.stringify(a)}...'` استفاده شده (با کوتیشن تکی) که اگه هر رشته‌ای تو آبجکت یک کوتیشن تکی داشته باشه، HTML می‌شکنه — قدیمیه، جدید نساختمش، ولی جای اصلاح داره.

## بخش ۲: فاز ۳ — تکالیف تعاملی

سه نوع پاسخ جدید به تکالیف اضافه شد:

### ۱) «نقاشی» (draw)
یک canvas ساده با قابلیت کشیدن با انگشت/ماوس + دکمه‌ی پاک‌کردن. مثل عکس، نتیجه به‌صورت data URL ارسال می‌شه و **دستی تصحیح می‌شه** (نقاشی رو نمی‌شه خودکار تصحیح کرد).

### ۲) «تطبیق» (match) — خودکار تصحیح می‌شود
معلم جفت‌های چپ/راست تعریف می‌کنه (حداقل ۲، حداکثر ۱۰). دانش‌آموز با tap یکی از سمت راست رو انتخاب، بعد جفتش رو از چپ می‌زنه. نمره فوراً و خودکار محاسبه می‌شه.

**نکته‌ی امنیتی مهم:** پاسخ درست هیچ‌وقت به مرورگر فرستاده نمی‌شه — دقیقاً مثل الگوی موجود سوالات چهارگزینه‌ای امتحان. هر جفت دو شناسه‌ی کاملاً نامرتبط و تصادفی داره (نه یک شناسه‌ی مشترک)، وگرنه مقایسه‌ی شناسه‌ها خودش جواب رو لو می‌داد.

### ۳) «دسته‌بندی» (drag_drop) — خودکار تصحیح می‌شود
معلم دسته‌ها + آیتم‌ها با دسته‌ی درست هرکدوم رو تعریف می‌کنه. دانش‌آموز برای هر آیتم از یک `<select>` دسته‌ی درست رو انتخاب می‌کنه.

**تصمیم طراحی:** به‌جای drag/drop واقعی HTML5 (که رو موبایل و لمسی خیلی نامطمئنه)، از dropdown استفاده شد — تجربه‌ی کاربری قابل‌اطمینان‌تر، خصوصاً برای بچه‌های دبستانی، با همون نتیجه‌ی نهایی.
