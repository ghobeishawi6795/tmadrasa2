# تست‌های امنیتی — قدم ۱۱-ب

این پوشه یک مجموعه تست end-to-end برای بررسی IDOR (دسترسی با تغییر ID)، ایزوله‌ بودن
مدرسه‌ها از هم، و مالکیت منابع (Ownership) بین معلم/دانش‌آموز/والد است. تست‌ها فقط از
طریق HTTP API واقعی اجرا می‌شن — یعنی قبول‌شدن یعنی خودِ API این قوانین رو رعایت
می‌کنه، نه فقط ساختار دیتابیس.

## اجرا

```bash
# 1) اجرای API به‌صورت لوکال
wrangler pages dev public --d1=DB --local

# 2) بارگذاری داده‌های آزمایشی (در یک ترمینال دیگر)
wrangler d1 execute madrese --local --file=tests/fixtures/security-fixtures.sql

# 3) اجرای تست‌ها
BASE_URL=http://127.0.0.1:8788 node tests/security-idor.mjs
```

خروجی موفق چیزی شبیه این می‌ده:

```
✓ admin B cannot delete school A's class
✓ admin B's student list excludes school A students
...
17 passed, 0 failed
```

اگر چیزی fail بشه، اسکریپت با کد خروج ۱ تموم می‌شه (قابل استفاده در CI).

## پاک‌سازی داده‌های تست

بعد از تست، دستورات `DELETE` در انتهای `tests/fixtures/security-fixtures.sql`
(الان به‌صورت کامنت هستن) رو از حالت کامنت خارج کن و دوباره با `wrangler d1 execute`
اجرا کن تا داده‌های آزمایشی (ID های ۹۰۰۰۰ به بالا) پاک بشن.

## چه چیزی تست می‌شه

| دسته | مثال |
|---|---|
| بین‌مدرسه‌ای (IDOR) | مدیر/معلم مدرسه B نمی‌تونه با حدس‌زدن ID به کلاس/آزمون/نمره مدرسه A دسترسی پیدا کنه |
| هم‌مدرسه، مالکیت متفاوت | معلمِ دیگری در همون مدرسه نمی‌تونه آزمون معلمِ اول رو ببندد/حذف کند |
| عضویت در کلاس | دانش‌آموزی که در کلاس عضو نیست نمی‌تونه در آزمونِ آن کلاس شرکت کند |
| مالکیت والد | والد فقط می‌تونه نمرات فرزند خودش را ببیند، نه دانش‌آموز دیگر |
| عضویت در گفتگو | کاربری که عضو یک مکالمه نیست نمی‌تونه پیام‌های آن را بخواند |
| Rate limiting ورود | بعد از ۵ تلاش ناموفق، حتی رمز درست هم رد می‌شود |
| احراز هویت پایه | بدون توکن یا با توکن جعلی، همه‌جا ۴۰۱ |

## یافته‌های بازبینی کد (بدون نیاز به اجرای تست)

این‌ها رو با خواندن کد تأیید کردم، نه با اجرا (چون این محیط به شبکه دسترسی نداره):

- **بدون وابستگی باقی‌مانده به `users.role`** — جدول `users` از ابتدا ستون role
  نداشته؛ همه‌چیز از `user_roles`/`roles`/`permissions` می‌آد. ✅
- **Session Token Hashing / Revocation / Expiration** — در `_shared/auth.js` از
  قبل درست پیاده شده: توکن خام هرگز مستقیم با دیتابیس مقایسه نمی‌شه، بلکه هش
  می‌شه و با `sessions.token_hash` مقایسه می‌شه؛ `revoked_at` و `expires_at` هم
  چک می‌شن. ✅
- **Rate limiting ورود** از قبل پیاده‌سازی شده (۵ تلاش/۱۵ دقیقه). ✅
- ⚠️ **Session Rotation** (چرخش توکن بعد از مدتی یا بعد از عملیات حساس) در
  نقشه‌راه قدم ۱۱ ذکر شده ولی پیاده نشده. این یک سخت‌گیری اضافه‌ست، نه یک باگ
  امنیتی حیاتی — پیشنهاد می‌کنم به‌عنوان یک بهبود آینده (نه بخشی از قدم ۱۱) نگه
  داشته بشه، مگر اینکه بخوای همین الان اضافه‌ش کنیم.
- ⚠️ **هیچ Admin API برای ساخت معلم/والد/درس (subject) وجود نداره.** جدول‌های
  `teachers`, `parents`, `subjects`, `teaching_assignments`, `parent_students`
  فقط از طریق دسترسی مستقیم به دیتابیس پر می‌شن (به همین دلیل fixture تست‌ها
  با SQL مستقیم ساخته شد، نه از طریق API). این یعنی مدیر مدرسه در حال حاضر از
  طریق داشبورد/API نمی‌تونه معلم جدید اضافه کنه یا والدی رو به فرزندش وصل کنه.
  این خارج از محدوده امنیتیِ قدم ۱۱ هست، ولی برای Production واقعی لازمه — اگه
  بخوای می‌تونیم به‌عنوان یک قدم جداگانه (یا زیرمجموعه‌ی ۱۱-ج) اضافه‌ش کنیم.
